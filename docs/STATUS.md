## Done in Phase 1

- **Ignore rules, schema 0.2.0** ([spec §7.2.1, §7.3](spec/diff-document.md)): `ignore.regex` masks each match with a per-pattern placeholder (a masked value still differs from a missing one), with deterministic limits (16 patterns, 1024 characters, 50000 NFA units) and a new `invalid-regex` error. `ignore.blankLines` turns blank-only changes into the new `ignored` op kind: not a change, not counted in stats, never a hunk of its own, and left out of the similarity denominator, so blank-only differences are `identical`. Re-blessing changed only `schemaVersion` and `id` in 74 of the 75 existing golden files; the other one, `text/018`, now masks its timestamps instead of being an `unsupported-option` error. Five new text cases (036–040); CLI, Python and WASM stay byte-identical on all 80 cases.
- **Canonical JSON writer:** documents are serialized straight to RFC 8785 text without a `serde_json::Value` tree. Two 32 MB inputs with a 107 MB document now peak at 0.6 GB footprint instead of 2.5 GB, with byte-identical output.
- **Moved-block detection** (`text.moves@1`, [moves spec §4](spec/text-granularity-and-moves.md)): pure moves (with indentation changes) and edited moves, `detectMoves: true` is supported, and moves never change hunks. On the 41 labelled cases: precision 1.00 and recall 1.00 (36 of 36 labels), kind accuracy 1.00, exact boundaries 0.81, no moves in the 9 negative cases. The conformance runner now gates on these metrics. Pure pieces of one moved block with an edited line inside are joined into one edited move (moves spec §4.3 step 4, case `moved/041`). Work is bounded by deterministic limits (`moves-skipped-limit`); the edited search compares small segment pairs first, so large unrelated churn no longer switches it off.

- **Line-diff core** ([ADR 0006](adr/0006-line-diff-library.md)): `text.histogram@1` and `text.myers@1` run on `gix-imara-diff` 0.3.3; Histogram has a deterministic work budget with a Myers fallback (200k swapped line pairs: 0.46 s instead of 33 s). Inputs over 256 MiB per side give `limit-exceeded`.
- **Spec alignment:** one source of truth for output shapes, options and warning codes ([diff-document.md](spec/diff-document.md)); LF, CRLF and lone CR all end a line; default granularity `line`.
- **Corpus:** 40 text cases (invalid UTF-8, UTF-16, mixed and lone-CR line endings, long lines, word/char/smart granularity) and 41 moved-block cases; 81/81 pass in strict conformance, which CI now enforces.
- **Canonical writer:** a direct RFC 8785 writer replaced the intermediate JSON tree; peak memory on a 1M-line, 107 MB result fell from 2.5 GB to 0.6 GB.
- **Large-file mode** ([ADR 0006, large-file mode](adr/0006-line-diff-library.md#large-file-mode)): through the CLI, the 1 GB log pair now takes 1.9 s and 536 MB peak footprint (was 8.5 s and 4.5 GB), the 100 MB pair 0.14 s and 52 MB (was 0.52 s and 416 MB), 5 M copies of one line 0.48 s and 205 MB (was 0.90 s and 561 MB), and a 1 GB file against itself 0.65 s and 58 MB (was 7.3 s and 4.4 GB). Outputs are byte-identical: no golden file was re-blessed, CLI, Python and WASM agree on all cases, and the large outputs match the previous build. How: memory-mapped input (`--no-mmap` to read), a 4-byte-per-line index instead of line records, byte-identical inputs decoded once, the common prefix and suffix trimmed before interning, keys borrowed from the text unless an ignore option normalizes them, both sides decoded and hashed on two threads (native only), and the canonical JSON and its `id` streamed instead of built as strings. `spikes/line-diff-bench/cli-bench.sh` reproduces the numbers with the real CLI.

- **Type detection and binary diff, schema 0.3.0** ([ADR 0009](adr/0009-type-detection-and-binary-diff.md), [spec §16–§18](spec/diff-document.md)): new crates `diffyman-detect` (`detect.sniff@1`: text or binary from the content only, UTF-8 and UTF-16 validity, NUL and control bytes in the first 8000 bytes; media type from `infer` 0.22.0 magic numbers or a small extension table) and `diffyman-adapter-binary` (`binary.bytes@1`: common prefix and suffix, byte-level Myers up to 64 KiB under a global work budget, FastCDC chunks with BLAKE3 for larger inputs). New kind `binary` with `bytes[]` ranges and `stats.bytes`, a new `adapter` option (`auto`, `text`, `binary`), and warnings `binary-fallback` and `bytes-coarse-limit`. Under `auto`, inputs that are not UTF-8 give a binary document instead of an `invalid-utf8` error. Re-blessing changed only `schemaVersion`, `id`, `options.adapter` and `stats.bytes: null` in 78 of the 81 existing golden files; the other three changed `mediaType` by detection (`text/csv`, `application/yaml`, and `application/octet-stream` for the Latin-1 side of 021). `text/021` and `text/022` now pin `adapter: "text"`. 16 new `binary/` cases (97 in all) pass strict conformance and `check_binary_expected.py`, which rebuilds each right input from the ranges; CLI, Python and WASM agree on all of them. Through the CLI a 256 MiB pair with 4096 scattered one-byte edits takes 0.8 s, and 64 hard 30 KiB regions stay within the budget (0.13 s).

Re-blessing changed only `id`, `options.tree` and `stats.tree: null` in all 97 existing golden files; 26 new `tree/` cases (123 in all) pass strict conformance, CLI and Python agree byte for byte on all of them and WASM on the 14 without a folder input. The `smart` noise check and whitespace merging in inline refinement are linear instead of spans × tokens, with byte-identical output.

Each `replace` op is aligned again by move key; lines that only changed indentation or terminator are in place, and the runs between them are sub-ops for rule 4.1.4, so a whole-file LF to CRLF conversion under whitespace `none` no longer hides moves (the old spec claim that a terminator change never prevents a move is now true). Lines over 256 graphemes are compared by their common prefix and suffix plus an exact bit-parallel distance of the remainders (at most 4096 graphemes each, under a 32M-step budget that ends in `moves-skipped-limit`), so a one-character edit in a long line keeps its block. The binary diff chunks a changed region that is still too large for byte alignment again at 1 KiB and 256-byte average chunks, then compares it position by position when that keeps at least half of it, so edits closer together than one chunk keep their own ranges (128 KiB with 30 eight-byte overwrites: 30 exact ranges, similarity 0.998, was one coarse range at 0.06). Child contents count against the 4 GiB per-side content budget, a nested tree sets its own size aside before its children use `tree.childBudget`, and no child is computed once the budget is below the smallest possible child: on a 17 KB pair of 16-way nested zips, `childBudget` 1 takes 0.0 s (was 26.6 s on the reported pair), the defaults 1.1 s with the 16 MiB budget filled, and budgets of 64 KiB and 4 MiB 0.3 s each instead of 3.0 s and 8.0 s with nothing embedded; `maxDepth` 16 is bounded by the content budget (6 s, was 69 s on the reported pair). ## Done in Phase 2

Every binding follows [ADR 0007](adr/0007-binding-strategy.md): one native call that returns the engine's canonical JSON unchanged, typed wrappers in the host language generated from the JSON Schema, and the engine's error rule (invalid options or an unreadable path raise; problems with the inputs are a document with `status: "error"`). No binding has diff logic of its own.

- **Python** ([README](../bindings/python/README.md)): PyO3, one abi3 wheel for CPython 3.11+, `diff`, `diff_document` and generated `TypedDict` types (`mypy --strict`); the GIL is released during a diff. 470 tests pass; `uv.lock` pins the development tools and their dependencies.
- **Node.js** ([README](../bindings/node/README.md)): a napi-rs addon (`@diffyman/node`, Node.js 22+) with `diff`, `diffDocument`, `diffPaths` and `...Async` variants on the libuv thread pool, `DiffymanError` with the engine's `code`, and TypeScript types generated from both schemas. A panic inside the engine is caught (on the thread pool too) and thrown as an `Error` with code `internal` instead of aborting Node.js. 870 `node:test` tests, including the whole corpus through all four entry points.

- **Review fixes** (schema 0.4.0 and the engine unchanged; [ADR 0012](adr/0012-local-service-architecture.md), the [API reference](api/README.md) and [OpenAPI](api/openapi.json) updated). Blobs belong to the key that uploaded them: migration `0002` adds `blob_grants` (one per key and blob, with that upload's own expiry); `POST /v1/jobs` accepts a blob only through the caller's live grant (or a saved diff the caller owns), so another key's upload is `404 blob-not-found` exactly like bytes never stored, and `POST /v1/blobs` answers `201` for bytes new to the caller and `200` only for the caller's own repeat, with the caller's dates. `DELETE /v1/diffs/{id}` and the sweeper remove a blob only when no job or saved diff references it and no key's grant is live, so one key can no longer delete another key's upload. Blob rows are now deleted and committed before their objects: a per-blob advisory lock, held on a connection of its own from before the rows go until the objects are gone (closed afterwards, so it ends on every path), orders this against uploads, which take it in shared mode and re-check the object; the delete runs on its own task, so a timeout cannot stop it halfway, and an object the store refuses to delete is left without a row for the orphan sweep (`204`, not `503` with rows pointing at deleted objects). Synchronous diffs are admitted before their body is read, by count (`DIFFYMAN_MAX_PARALLEL_DIFFS`, one per core) and by a shared memory budget (`DIFFYMAN_SYNC_MEMORY_BYTES`, 1 GiB, four bytes per declared body byte), and the reservation stays until the engine thread returns, even after a timeout. A job keeps its slot until its result is stored and committed and its engine thread is done, and the summary of a document is read without parsing the whole document into memory. Regression tests: 2 database tests (grants, delete locks), 1 unit test (admission), 5 HTTP tests (blob ownership and no existence leak, deletes that keep another key's upload, a refused object delete, admission before the body, the job slot held until commit), and one more end-to-end check. Also: `.gitignore` covers `*.dump` and `*.dump.sha256`, and the fuzz and spike manifests have `homepage`.
- **Request and job hardening** (schema 0.4.0 and the engine unchanged; [API reference](api/README.md), [server guide](server.md) and [ADR 0012](adr/0012-local-service-architecture.md) updated, `.sqlx/` refreshed). A cancel accepted while a job runs now always wins: the final update of a job ends it `cancelled` instead of `succeeded` when a cancel was requested, and the worker rolls back the saved diff it wrote with it, so a result that arrives after the cancel is discarded. A NUL character (U+0000), which PostgreSQL cannot store in `text` or `jsonb`, is refused in input names and in a job's options before any query with the new code `400 nul-character` (also in key names), and the SQLSTATEs `22021` and `22P05` map to the same typed error instead of `500`. Job input names keep only their last path component (split on `/` and `\`, as the engine does), so a full path is never stored or shown. An invalid JSON body gets a fixed message with its line, column and kind (`syntax`, `eof`, `data`, `io`) instead of serde's text, which quoted the request's values and field names. Connections have a header-read limit (`DIFFYMAN_HEADER_READ_TIMEOUT_SECS`, 10 s, from the connection's start or the first byte of a later request) and an idle limit between requests (`DIFFYMAN_IDLE_TIMEOUT_SECS`, 60 s), kept apart from each other (hyper's own header timeout would also have closed every kept-alive connection after 10 s). Regression tests: 4 database tests (a cancel before the result, a result without a cancel, NUL in `text` and in `jsonb`), 3 unit tests, and 9 acceptance tests against the router or the real listener: the cancelled job keeps no result, full-path job names, NUL in job names, job options and synchronous names refused with no database reachable, invalid JSON bodies whose values and keys never appear in the answer, a trickled request head and a silent connection closed after the header-read limit, and a kept-alive connection still usable after it but closed after the idle limit.
- **Resident memory of synchronous diffs** (the API and the engine unchanged; [ADR 0012](adr/0012-local-service-architecture.md) and the [API reference](api/README.md) updated). `DIFFYMAN_SYNC_MEMORY_BYTES` bounded the memory diffs were admitted with but not the process: the system allocator kept freed large blocks resident (on macOS a cache of them, which `malloc_zone_pressure_relief` does not empty), so 40 parallel diffs of 16 MiB bodies within a 256 MiB budget peaked at 628 MiB and stayed near 570 MiB idle. `diffyman-server` now runs with its own global allocator (`src/alloc.rs`): blocks of 1 MiB or more are mapped from the operating system and unmapped when freed, smaller ones go to the system allocator. The same 40 diffs peak at 121 MiB (bound 331 MiB) and leave about 50 MiB; the 200 MB job peaked at 606 MiB in 1.23 s. Regression tests: 4 unit tests of the allocator (the threshold, contents kept across reallocations in both directions, zeroed blocks, and no page of a freed large block left resident).
- **Request validation fixes** (the engine unchanged; [API reference](api/README.md) and [server guide](server.md) updated; `tests/server/test_validation.py` now passes all 27 tests, it failed 4). Options are kept as their JSON text and read with the engine's strict parser (`diffyman::parse_options_json`), so an object that gives a key twice, at any depth, in a JSON body, a job request or a multipart `options` field, is `400 invalid-options` as with `diffyman diff --options`, instead of serde keeping the last value. `invalid-options` messages are one of three fixed texts and name no field, since the engine's message quotes unknown or repeated keys and wrong values. hyper's own bodiless answers to request heads it cannot parse (a malformed request line or header, the bytes after an understated `Content-Length`, a target over 65,534 bytes, a head with more than 100 headers) are replaced on the way out by a typed error with `X-Request-Id` and a log line: `400 invalid-request`, `400 invalid-blob-id` for an over-long `?sha256=` value, or the new `431 headers-too-large`; the throughput of small diffs is unchanged (1,128 requests/s). A request with two `Host` headers gets `400 invalid-request` instead of being checked on the first. Regression tests: 5 unit tests (repeated keys as the CLI refuses them, fixed messages, which hyper answers are replaced and which are left alone, the `?sha256=` case) and 7 acceptance tests against the router or the real listener (repeated keys in every request form, messages that never quote the options, a 64 KiB target, an over-long `?sha256=` value alone and on a kept-alive connection, bytes past an understated `Content-Length`, malformed and oversized heads, two `Host` headers).
- **Kept-alive connections after a refusal** (the engine and the error codes unchanged; [API reference](api/README.md) updated). The CI database job failed at the 200 MB upload of `run_e2e.py` with a broken pipe while sending the request head, on a connection last used for a refused `PUT /v1/diff`. When the server answered a request without reading its body (a refused method or `Host`, a missing key) and the body had not arrived with the head, hyper closed the connection after the answer without `Connection: close`; that happened to about 2% of such requests on macOS and on Linux (arm64 and x86_64), and the harness resent a failed request on a new connection except when its body was a stream. The allocator was ruled out: its tests pass on Linux in CI, and `run_e2e.py` passed with it in Ubuntu 24.04 containers. Bodies with a `Content-Length` of at most 64 KiB are now read before a request is handled (within the request time limit), so a refusal leaves the connection open; larger and chunked bodies are still refused without waiting for them. The harness client reopens a connection the server has closed before sending on it, takes an answer sent before the body as the reply, rewinds and resends a file body once, and prints the server log's tail when it gives up; `run_e2e.py` says whether the server was still running and copies the server log with `--server-log`, and the CI job uploads the server logs when it fails. Regression tests: 2 acceptance tests against the real listener (a late body after a refused method or `Host` leaves the connection usable; a refusal with a 10 MB declared body is answered at once). The slot test of `test_limits.py` now sends bodies over 64 KiB, so they still hold the diff slots. Against the fix, refused requests closed 0 of 300 connections; `run_e2e.py` passed all 789 checks on macOS and in Ubuntu 24.04 containers (arm64, and x86_64 emulated), and `test_validation.py` (27 tests) and `test_limits.py --scale ci` (20 tests) passed on macOS, and in the x86_64 container too (there the 10 tests of the `requests` group).

## Moved to later phases

- **Phase 3 (local platform):** `childRef`, for services that store child documents apart from their parent.
- **Phase 4 (formats):** legacy text encodings (for example Latin-1 on request); bzip2, xz and 7z; the content of modified archive entries in the unified format and the HTML report (today only for two folders: archive entries would need a second listing of each archive, as costly as the comparison, unless the tree adapter can read one entry by path or the engine hands out child contents while it has them).
- **Later tuning (no phase fixed):** a binary diff whose chunk alignment leaves a changed region over 64 MiB goes straight to the position-by-position step (exact for overwrites, flagged `bytes-coarse-limit`), as in a 256 MiB pair with 4096 scattered one-byte edits; under `ignore.whitespace` `all`, `moved/027` and `moved/046` lose their move and 046 gets a short false one (not yet investigated); joining an edited line above a pure piece (moves spec 4.3 step 4 only walks down), so a block whose first lines changed can come out as an edited and a pure move instead of one; `--no-mmap` reads a regular file whole before the 4 GiB binary limit refuses it (by design: it gives the same error document as the mapped default; `--max-input-size` bounds it).
