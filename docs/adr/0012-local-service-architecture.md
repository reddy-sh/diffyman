# 0012. Local service architecture

- **Status:** Accepted
- **Date:** 2026-11-08

## Context

Phase 3 adds `diffyman-server`, a local REST service over the same engine, with PostgreSQL for state (ADR 0003) and object storage for content (ADR 0004). It must run on one laptop today and move to a managed cloud later by changing configuration only. It handles files from people it does not trust, on a machine that also runs a browser, so it must be safe by default: loopback only, authenticated, bounded in size, time and memory, and forgetful (content expires). The engine, CLI and bindings must stay free of databases, networking and async runtimes.

## Decision

**Crates.** Three new crates, the only ones allowed to depend on `sqlx`, `object_store` or `tokio`:

- `diffyman-storage`: the `BlobStore` trait (put from bytes or a stream with SHA-256 verification, get as a stream or a byte range, head, delete, list by prefix) over `object_store` 0.14.2. `file://` and `memory://` are built in; `s3://` is behind the Cargo feature `s3`. Keys are content-addressed, `blobs/sha256/<first two hex digits>/<64 hex digits>`, and the blob ID is the lowercase hex SHA-256. A streamed put writes to `staging/<uuid>` while hashing, checks the size limit and the expected hash, then renames to the final key; a byte put hashes first and writes the final key directly. The file store writes every object to a temporary file and renames it, so a reader never sees a partial blob.
- `diffyman-db`: `sqlx` 0.9.0 on PostgreSQL 18 with compile-time checked queries, forward-only SQL migrations in `crates/diffyman-db/migrations` embedded in the binary, and offline query data in `.sqlx/` so builds need no database (`SQLX_OFFLINE=true`). `sqlx.toml` renames the query-checking variable to `DIFFYMAN_DB_URL`, so an unrelated `DATABASE_URL` never leaks in.
- `diffyman-server`: the `diffyman-server serve` and `diffyman-server keys` commands, the configuration, the HTTP layer (axum 0.8.9 on tokio, HTTP/1.1, an OpenAPI 3.1 document from utoipa 6.0.0 served at `/openapi.json` and kept in `docs/api/openapi.json` by a test that fails when it is stale), the job worker and the sweeper. It builds the engine with archive support and without the `fs` feature, so the server never reads a path on disk.

**Configuration** is layered: built-in defaults, then `diffyman.toml` (the path in `DIFFYMAN_CONFIG`, or `./diffyman.toml` when present; unknown keys are errors), then `DIFFYMAN_*` environment variables. With `DIFFYMAN_ENV=local` (the default) the server also reads `.env.local` from the working directory, only for names not already set, and refuses it when group or others can read it; without `DIFFYMAN_DB_URL` it then builds the local URL from `DIFFYMAN_PG_PASSWORD`. Under `DIFFYMAN_ENV=prod`, `.env.local` is never read and `DIFFYMAN_DB_URL` is required. Secrets never appear in `Debug` output or logs.

**Schema** (migration `0001`): `api_keys`, `blobs` (one row per stored object, with size, media type and expiry), `jobs` (UUIDv7 IDs from PostgreSQL 18's `uuidv7()`), `diffs`, `usage` and `audit`. References between rows are foreign keys to `blobs`, with no counters: a blob is in use exactly when a job or diff row points at it, and the database refuses to delete it while one does. `usage` and `audit` are append-only, enforced by triggers that reject `UPDATE`, `DELETE` and `TRUNCATE`. Migration `0002` adds `blob_grants`: one row per key that uploaded a blob, with that upload's own expiry (see Authentication and Retention).

**API (v1).** `POST /v1/diff` takes two small inputs (JSON with `text` or `base64` per side, or `multipart/form-data`; 8 MiB per side and a 24 MiB body by default) and returns the engine's canonical JSON bytes untouched, with `provenance.binding` set to `server`; with `?save=true` it also stores the document and both inputs and answers `201` with `Location: /v1/diffs/{id}`. `POST /v1/blobs` streams an upload into the store (blob ID = SHA-256, optional `?sha256=` check). `POST /v1/jobs` diffs two blobs, or a blob and one side of a saved diff, in the background; `GET /v1/jobs/{id}` reports its status and result link; `POST /v1/jobs/{id}/cancel` cancels it (a separate action rather than `DELETE`, because the job record stays). `GET` and `DELETE /v1/diffs/{id}`, `GET /v1/formats`, `GET /healthz` and `GET /openapi.json` complete the set. Errors are `{"error": {"code", "message"}}` with stable kebab-case codes listed in the OpenAPI document. Synchronous diffs are admitted before their body is read: at most `max_parallel_diffs` at once (one per CPU core by default) and together within `sync_memory_bytes` (1 GiB by default), each reserving four bytes per byte of its declared body (the body limit when no `Content-Length` is given). A request waits for admission at most half its time limit, then gets `503 busy`. What it was given is held until the request is done and the engine has returned, even after a timeout, so neither bodies in memory nor engine threads still running exceed the limits. The binary's global allocator maps every block of 1 MiB or more from the operating system and unmaps it when it is freed (smaller blocks go to the system allocator): the system allocators keep freed large blocks resident for reuse (macOS caches them, glibc keeps them in per-thread arenas), which let 40 parallel diffs within a 256 MiB budget hold 628 MiB, and 570 MiB once idle.

**Job queue.** Jobs are rows. A worker claims up to N queued jobs with `FOR UPDATE SKIP LOCKED`, which sets a lease (owner and expiry) and counts the attempt. It renews the lease with heartbeats (the first right after the claim, then every third of the lease), which also report a cancellation request, and finishes with a guarded update that only succeeds while it still owns the lease; the saved diff and the job's success are written in one transaction. A cancel requested while the engine ran wins: that update then ends the job `cancelled` instead, and the transaction with the saved diff is rolled back. A sweeper puts jobs with expired leases back in the queue, or fails them with `lease-expired` after the last attempt. Each process runs `max_parallel_jobs` jobs at once (half the CPU cores, between 1 and 4, by default). A job is admitted only when its inputs together fit a quarter of `job_memory_bytes`. The engine cannot be interrupted, so a job past its time budget, or cancelled while running, is ended in the database at once while its blocking thread keeps its slot until the engine returns: the number of engine threads never exceeds the slots. A slot is also held while the document is stored and the result committed, so no more than `max_parallel_jobs` jobs hold memory at once. Only infrastructure errors (`503`: database or blob store unavailable) are retried, after a delay that grows with the attempt; errors of the inputs or options fail the job at once. On shutdown, running jobs get a grace period and are then handed back to the queue.

**Authentication.** On first start the server writes a random 256-bit admin token to `~/.diffyman/admin-token` (or the configured path), created exclusively with mode 0600, never logged and never stored in the database. It only creates and revokes API keys: `diffyman-server keys create|list|revoke` run only for someone who can read that file, and talk to the database directly with the server's configuration. There is no HTTP route for keys, so the API has no admin surface and the token never crosses the network. Every `/v1` route needs `Authorization: Bearer <API key>`; `/healthz` and `/openapi.json` do not. Keys carry the scopes `read` (GET), `write` (POST) and `delete` (DELETE), all three by default, and an optional per-key rate limit (600 requests a minute by default, through `governor`). Jobs and saved diffs belong to the key that created them; other keys get `404`. Blobs are stored once by content but used by grant: an upload gives the uploading key a grant with its own expiry, and a job may use a blob only through the caller's live grant (or a saved diff the caller owns). `POST /v1/blobs` answers `201` when the bytes are new for the caller and `200` only when the caller had uploaded them before, with the caller's own dates, so no answer tells one key whether another stored the same bytes. API keys are 256-bit random values (`dmk_` and 64 hex digits). The database stores a 12-character prefix for lookup and a BLAKE3 hash in its key-derivation mode under a fixed context string (a keyed hash with domain separation), compared in constant time. There is no server-side pepper: it would add a secret to manage without making a 256-bit key any harder to guess. Argon2 was rejected: it protects low-entropy passwords, while a 256-bit random key cannot be brute-forced, and a deliberately slow hash on every request would hand attackers a cheap way to burn CPU.

**Request safety.** The listener binds `127.0.0.1:8080` by default, and the `local` environment refuses any address that is not loopback. Every request must carry an allow-listed `Host` header (defence against DNS rebinding) and is refused with `403` when it has an `Origin` that is not allow-listed (none by default); allow-listed origins get CORS headers and preflight answers. Connections must send a request's headers within 10 s (from the connection's start, or from the first byte of a later request) and are closed after 60 s without a request; the two limits are kept apart, because hyper's own header timeout would also end every kept-alive connection after 10 s. Request bodies, blob sizes, request time, job time, job memory (admitted by input size; a worker process with operating-system limits is future work) and parallel jobs all have configured limits. Errors are typed JSON with stable kebab-case codes, and their messages never quote the request (an invalid JSON body gets its position and the kind of error, not serde's text). A NUL character, which PostgreSQL cannot store in `text` or `jsonb`, is refused in input names and job options before any query (`400 nul-character`), and the SQLSTATEs `22021` and `22P05` map to the same typed error. Logs and traces carry IDs, sizes and timings only, never file content, names or paths: the server's log layer writes only its own events and only fields on an allowlist, so a field added carelessly is dropped rather than printed, and events of the HTTP, database and storage libraries are not written at all. The admin token's location is printed once on the terminal at start; its value never is.

**Retention.** Blobs, jobs and saved diffs get an expiry (30 days by default). A sweeper deletes expired rows and grants, and then blobs that are expired and no longer held. `DELETE /v1/diffs/{id}` removes the diff, the job that produced it and every blob that nothing holds any more: no other job or saved diff references it and no key's grant is live, so one key's delete never removes another key's upload. Blob rows are deleted and committed first, and only then are the objects removed: a failure part-way leaves objects without a row, never a row without its object. An advisory lock per blob (the first 64 bits of its SHA-256) orders this against uploads: the deleter (or sweeper) holds it in exclusive mode on a connection of its own, from before it deletes the rows until the objects are gone, and the connection is closed afterwards, so the lock ends on every path; it runs on a task of its own, so a request timeout cannot stop it halfway. An upload writes its object first (its ID is only known once it is hashed) and then, under the shared lock, inserts the row or extends its expiry; when the insert created the row, the object is checked once more, and if a delete or sweep removed it in between the upload is refused as `503 storage-conflict` and can be repeated. So a row never points at a missing object, and an object without a row (a failed upload or deletion) is removed by the sweeper after a grace period.

**Local and cloud.**

| Concern | Local | Cloud |
|---|---|---|
| Database | PostgreSQL 18.6 in Docker on `127.0.0.1:5433` | Managed PostgreSQL 18, TLS required |
| Blobs | `file://` folder `~/diffyman-data/blobs` | `s3://` bucket, encrypted at rest |
| Job queue | `jobs` table | The same table |
| Secrets | `.env.local` (mode 0600) | Secrets manager, injected as environment variables |
| Admin token | File with mode 0600 | Secret injected at start |
| Listener | `127.0.0.1:8080` | `0.0.0.0:8080` behind a TLS load balancer |
| Temporary files | `~/diffyman-data/tmp` | Container scratch disk |

Rejected: a separate queue service (one more moving part; the table is enough until measured otherwise), reference counters on blobs (they drift on partial failures; foreign keys cannot), the `config` crate (its environment mapping hides the variable names we want to document; a small loader on `serde` and `toml` is explicit and testable), `#[sqlx::test]` (it fails instead of skipping when no database is reachable), an HTTP route for creating keys (an admin surface on the network for a task done once), and `tower-http` for limits and timeouts (its rejections are plain-text bodies; small middlewares give the typed errors).

## Consequences

- The engine, CLI and bindings build exactly as before. `cargo test --workspace` passes without a database: database tests print a skip message unless one is reachable at `DIFFYMAN_TEST_DB_URL` (or the local default from `.env.local`), and `DIFFYMAN_TEST_DB_REQUIRED=1` turns the skip into a failure for CI jobs with a PostgreSQL service. Each test runs in its own schema of the `diffyman_test` database, never in the main one.
- The server's HTTP tests run without a database against a pool that never connects (authentication, `Host` and `Origin` checks, size limits, typed errors, the listener and its shutdown, and every corpus case whose inputs are files, which must give the CLI's document byte for byte apart from `provenance`); the tests of keys, jobs, cancellation, saved diffs and retention use the same per-test schemas as `diffyman-db` and skip the same way.
- A change to any query needs `cargo sqlx prepare --workspace` against a migrated database and a commit of `.sqlx/`.
- `object_store` is pre-1.0, so its upgrades may break the storage crate; the trait keeps that inside one crate.
- The `s3` feature brings an HTTP client with `aws-lc-rs`, which compiles C code, so a static musl image with S3 support needs a C toolchain at build time; the default build has no C dependency. Its certificate verifier depends on `webpki-root-certs` (root certificate data under CDLA-Permissive-2.0) on wasm32 targets only, which `deny.toml` allows for that crate alone.
- PostgreSQL connections use rustls with the platform's root certificates; `webpki-roots` is avoided for the same license reason.
- Revisit when one server is not enough (shared cache, a queue service), when OIDC joins API keys, or when jobs need process isolation.
